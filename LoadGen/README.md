# LoadGen

Генератор HTTP-нагрузки для демо-стенда DiagLab. Консольное приложение на .NET 10 без внешних
зависимостей, работает одинаково на Windows, Linux и macOS.

Пришёл на смену генератору на PowerShell, и вот почему.

* **Скорость.** Скрипт на PowerShell упирался сам в себя и выдавал десятки запросов в секунду.
  Генератор на `HttpClient` выдаёт тысячи, поэтому частоту приходится задавать явно (см. ниже).
* **Две модели нагрузки.** Кроме «N клиентов» есть «N запросов в секунду». Для курса это важно:
  часть проблем закрытая модель прячет, а открытая показывает (см. «Две модели нагрузки»).
* **Точное число запросов.** Ключ `-n 2000` даёт ровно 2000 запросов, что удобно, когда прирост
  чего-либо нужно сопоставить с числом операций.
* **Перцентили задержки** и живая статистика раз в секунду.
* **Сценарии в файле** `loadgen.json`: их можно добавлять и менять без перекомпиляции.

## Установка

Из корня репозитория:

```bash
dotnet pack LoadGen -c Release
dotnet tool install --global --add-source LoadGen/nupkg DiagLab.LoadGen
```

После этого в любом терминале доступна команда `loadgen`, так же как `dotnet-counters` и остальные
инструменты курса.

Обновление после правок в коде генератора:

```bash
dotnet tool uninstall --global DiagLab.LoadGen
dotnet pack LoadGen -c Release
dotnet tool install --global --add-source LoadGen/nupkg DiagLab.LoadGen
```

Без установки:

```bash
dotnet run --project LoadGen -c Release -- search -d 60
```

Всё, что стоит после `--`, передаётся генератору.

Команды одинаковы в PowerShell, bash и cmd.

Файл сценариев ищется сначала в текущем каталоге, затем рядом с программой (у установленного
инструмента — его собственная копия `loadgen.json`). Чтобы поменять сценарии без переустановки,
положите свой `loadgen.json` в каталог, откуда запускаете `loadgen`, или укажите его ключом
`--config`.

## Быстрый старт

```bash
loadgen --list                     # какие сценарии есть
loadgen mixed -d 120 -c 8          # всё сразу, 8 клиентов, 2 минуты
loadgen search -d 120              # поиск, 30 запросов/с (значение сценария по умолчанию)
loadgen rates -d 90 --rps 300      # 300 запросов/с независимо от того, успевает ли сервис
loadgen subscribe -n 1000 -c 8     # ровно 1000 запросов
```

Во время работы раз в секунду печатается строка статистики:

```text
  время   отпр/с  готово/с  в полёте  ошибки      p50      p95      p99     макс
  00:01    300.0     296.0        37       0   123 мс   126 мс   131 мс   140 мс
```

| Колонка | Что означает |
|---|---|
| `отпр/с` | сколько запросов ушло за секунду |
| `готово/с` | сколько ответов пришло |
| `в полёте` | отправлены, но ещё без ответа |
| `ошибки` | ошибки HTTP, таймауты, отказы в соединении |
| `p50`…`макс` | задержка успешных ответов |

В конце печатается итог. Ключ `--json итог.json` сохраняет его в файл, например для сравнения
«до» и «после» исправления.

## Две модели нагрузки

**Закрытая** (`-c N`, по умолчанию 8 клиентов). Каждый клиент отправляет следующий запрос только
после ответа на предыдущий. Если сервис замедлился, нагрузка сама падает: клиенты ждут. Так ведут
себя браузер одного пользователя и пакетная обработка.

**Открытая** (`--rps N`). Запросы уходят с заданной частотой, отвечает сервис или нет. Так
выглядит настоящий трафик: пользователи не знают, что сервису плохо, и продолжают приходить.

Разница принципиальная. Закрытая модель скрывает деградацию: сервис тормозит, клиенты ждут,
нагрузка падает, и система находит равновесие. Открытая модель деградацию обнажает: очередь
растёт, пока сервис не начнёт успевать или не упадёт.

В открытой модели число запросов в полёте ограничено ключом `--max-inflight` (по умолчанию 1000),
чтобы генератор сам не исчерпал память и сокеты. Запросы сверх предела не отправляются и
учитываются в итоге как «Пропущено». Это прямой признак того, что сервис не справляется.

У сценария в `loadgen.json` может быть своя модель по умолчанию (`"rps"` или `"concurrency"`).
Ключи `-c` и `--rps` в командной строке всегда важнее.

## Все параметры

```text
loadgen [сценарий] [параметры]
loadgen --url <адрес или путь> [параметры]
```

| Ключ | Назначение | По умолчанию |
|---|---|---|
| `-s`, `--scenario` | сценарий из `loadgen.json`; можно просто первым словом | `mixed` |
| `--url` | разовый запрос без файла сценариев | |
| `-m`, `--method` | HTTP-метод для `--url` | `GET` |
| `--body` | тело запроса для `--url` | |
| `--content-type` | тип тела для `--url` | `application/json` |
| `-l`, `--list` | показать сценарии | |
| `-d`, `--duration` | длительность: `90`, `30s`, `2m`, `00:01:30` | 60 с |
| `-n`, `--requests` | ровно N запросов; без `-d` работает до их завершения | |
| `--warmup` | прогрев: нагрузка идёт, но в итог не попадает | |
| `-c`, `--concurrency` | закрытая модель, N клиентов | 8 |
| `-r`, `--rps` | открытая модель, N запросов в секунду | |
| `--max-inflight` | предел одновременных запросов в открытой модели | 1000 |
| `--delay` | пауза клиента между запросами, мс | 0 |
| `--timeout` | таймаут одного запроса | 30 с |
| `-u`, `--base-url` | адрес сервиса | из `loadgen.json` |
| `--config` | другой файл сценариев | |
| `--interval` | период живой статистики; `0` выключает | 1 с |
| `--json` | сохранить итог в JSON | |
| `--no-health` | не проверять доступность сервиса перед стартом | |

Подстановки в шаблонах пути и тела:

| Шаблон | Что подставляется |
|---|---|
| `{seq}` | номер запроса в запуске: 1, 2, 3… |
| `{run}` | идентификатор запуска, уникальный между запусками |
| `{rand:1:500}` | случайное целое, границы включительно |
| `{pick:EUR\|USD}` | случайный элемент списка |
| `{guid}` | новый GUID |

Пример разового запроса:

```bash
loadgen --url "/api/reports/export?rows=664" -c 4 -d 20
```

## Как устроен

Один `HttpClient` на весь прогон: соединения переиспользуются, и генератор сам не создаёт сокеты
в `TIME_WAIT`. Иначе при подсчёте соединений его сокеты смешались бы с сокетами исследуемого
сервиса.

Задержки пишутся в гистограмму без блокировок, одной атомарной операцией. Генератор не должен
сам создавать конкуренцию за блокировки, которую курс учит находить.

В открытой модели задержка отсчитывается от момента, когда запрос **должен был** уйти по
расписанию, а не когда реально ушёл. Если генератор отстал, отставание попадёт в задержку.
Без этого (ошибка coordinated omission) перцентили выглядят лучше, чем есть.

Если сервис несколько секунд подряд отказывает в соединении и не присылает ни одного ответа,
генератор останавливается с сообщением: процесс сервиса, скорее всего, упал, и лить нагрузку
дальше бессмысленно. Код завершения в этом случае — 3.

| Файл | Содержимое |
|---|---|
| `Program.cs` | разбор параметров, проверка сервиса, запуск |
| `CliOptions.cs` | ключи командной строки и справка |
| `Config.cs` | загрузка `loadgen.json`, сценарии и смеси |
| `Template.cs` | шаблоны с подстановками |
| `Runner.cs` | две модели нагрузки, выполнение запросов, наблюдение за доступностью |
| `Stats.cs`, `Histogram.cs` | счётчики и гистограмма задержек |
| `Report.cs` | вывод в консоль и в JSON |
